Plain-English guide

What is this app, and how do I show, test and understand it?

When something breaks at work ("the app is slow", "I can't log in"), a support engineer wants four answers fast: has this happened before? what fixed it? what should I try first? who takes over if it fails? This app answers by comparing the new problem with a library of 3,130 past incidents, recommending one first step with the proof behind it, guiding the engineer step by step, and learning from every fix.

1. Evidence before opinion

Every recommendation lists the past incidents that back it. Nothing is a bare claim.

2. "I don't know" is an answer

If nothing similar exists it says Novel incident and does not invent a fix.

3. A human stays in charge

It never touches a real system. Risky steps (restart, delete) are marked "needs human confirmation".

How to use this page

  • New to the project? Read section 3, then do the 10-minute click tour in section 2.
  • "What does this button do?" Go to section 4 and type the button's name in the search box.
  • "What does this result mean?" Section 5 shows the screen with numbered callouts, and explains every field of the response.
  • Want to prove it works? Section 7 has about 90 test cases with a tick box each; your ticks are remembered in this browser.
  • Want to play with the maths? Section 6 has small calculators (confidence, grade, novelty, tier, quality gate) and a troubleshooting simulator.
How much of this was actually checked? Observed = I ran it against your live API on 2026-09-29 and copied the real result. Code = read from the source code or automated tests but not clicked by hand. Every test case is labelled, so you know how far to trust it. Numbers move slightly as the library grows, so compare the verdict and grade, not the fourth decimal.

Start the app (two terminals, both in the project folder)

Terminal 1: the engine (API) 
venv\Scripts\activate
uvicorn backend.main:app --port 8000

Wait for Application startup complete (about a minute the first time, while models load). Your folder has venv, not .venv.

Terminal 2: the screens (website) 
cd web
npm install     # first time only
npm run dev

Open http://localhost:3000 on a laptop or desktop (at least 1200 px wide; there is no phone layout).

Is it healthy? Open localhost:8000/health. When I checked: status: ok, search index 3130 vectors, local embeddings + local re-ranker, 3,130 records, 30 families, tiers L1, L2, L3, and an AI writer available (gpt-4o-mini, so an AI key is set on this machine). If the engine is off, every screen says "Could not load this view." and the menu's status panel shows API offline.

A. The 10-minute click tour best for a demo

  1. Assistant → "Memory leak" → Analyze. Blue Known pattern bar, family F001, first step "Restarting the application service", confidence about 0.45 shown as a sum, grade Good.
  2. Assistant → "Tape robot (unseen)" → Analyze. Red Novel incident bar, no fix, grade Poor. This is the honesty moment.
  3. Assistant → Memory leak → Start guided troubleshooting → Start troubleshooting. Click It failed three times. Watch the step get crossed out each time.
  4. After the third failure the app asks one question ("Did this start after a recent deployment or configuration change?"). Answer it. Nothing new is found, so it escalates to L2.
  5. Escalations. Open the new item, read the hand-off packet (failed steps crossed out), type what fixed it (10+ characters), click Mark resolved.
  6. Knowledge base. See whether the fix was added, or is waiting under Manual review.
  7. Patterns → F001. Show the family, its fixes and how often each was reopened.
  8. Evaluation. Click the five presets one by one: Good, Fair, Poor, Poor, Poor.

Heads-up: this tour creates real records in the demo database (an incident, a session, an escalation, maybe a knowledge-base entry).

$b = @{ text = "Nothing comes out of the printer, documents stay in the queue" } | ConvertTo-Json
(Invoke-RestMethod -Method Post -Uri http://localhost:8000/incidents/resolve -ContentType "application/json" -Body $b).top_resolution

$b = @{ preset = "vpn-storm"; reset = $true } | ConvertTo-Json
(Invoke-RestMethod -Method Post -Uri http://localhost:8000/incidents/simulate -ContentType "application/json" -Body $b).alerts

3. The big picture

Three floors: data prepared once, an engine that answers questions, and the screens you click.

Floor 1 · prepared once

The library

Two raw files (46,606 real tickets) are cleaned, given AI-written text where text was missing, quality-checked, grouped into 30 families and indexed for search.

Floor 2 · the engine (port 8000)

FastAPI + three agents

Understand → search → re-rank → fingerprint → family → known/novel → one fix → safety → explain. Plus troubleshooting, escalation, correlation and learning.

Floor 3 · the screens (port 3000)

Next.js website

Assistant, Troubleshooting, Escalations, Novel incidents, Patterns, Knowledge base, Feedback, Evaluation. (An older Streamlit app also exists.)

Why each step exists
  • Understand: people don't write like log files. "Takes forever" becomes performance degradation so the search finds tickets that say "heap exhausted". A report is "vague" if it has 9 or fewer meaningful words or a specificity score under 0.4.
  • Two searches: meaning-search handles paraphrases but can miss exact codes ("ZX-99"); keyword search is the opposite. Both return 50 candidates; Reciprocal Rank Fusion (k = 60) merges by rank because their scores are on different scales. 22 identical tickets count as one piece of evidence.
  • Re-rank: a cross-encoder reads your text and each candidate together (top 30), and its score is calibrated into "how likely is this truly relevant?" (the percentage you see).
  • Known or novel: four real signals (best re-ranker score, best meaning similarity, closeness to a family centre, share of that family sharing your symptom) are blended into P(known). The cut-off 0.4896 was chosen to catch as many genuinely new incidents as possible while wrongly calling a known one "novel" no more than 2% of the time. With degraded search the verdict is Undetermined.
  • One fix: past fixes are grouped into strategies. Poor notes ("closed", "fixed") are skipped. If a family matches strongly (0.5+), its own strategies get a boost so the next suggestion after a failure is another way of fixing the same problem.
  • Safety: destructive words need 2+ independent past sources and human confirmation; disruptive words (restart, failover…) carry a confirm-with-owner note.

The confidence number, worked out

confidence = best relevance × agreement × provenance factor

Real example ("Memory leak" preset):
   0.9612   ×   0.5856   ×   0.8   =  0.4503
  (best match   (58.6% of the   (evidence is AI-written,
   is 96%        evidence backs    so it counts ×0.8)
   relevant)     this strategy)
Why it can never reach 1.0

About 95% of the library text is AI-written, so the provenance factor is almost always 0.8. That caps confidence near 0.80 on purpose. It is never guessed by an AI; if results were not re-ranked it shows "undetermined". Printer example: 0.977 × 0.911 × 0.8 = 0.712. Vague example: 0.739 × 0.509 × 0.8 = 0.301.

  1. The verdict. Blue = known pattern, red = novel, dark = undetermined. This is always read first.
  2. The family the incident belongs to (a link) and how strongly it matches (0 to 1).
  3. P(known): the chance this is a known problem, next to the tested cut-off 0.490. Above = known.
  4. Query evaluation: a one-line grade of how well the library can answer this query. Details opens the Evaluation page.
  5. The one recommended first step. Taken from the best-supported past fix, never generated from thin air.
  6. Confidence shown as a sum, so you can see where it came from. Below 0.45 on a vague report triggers a clarifying question in Troubleshooting.
  7. The proof: past incidents behind it (each is a link) and how many are AI-written (synthetic) vs real (original).
  8. Safety note. Present for disruptive or destructive actions. Absent for the printer driver fix.
  9. Next actions. Start guided troubleshooting (carries your report over) or rate the recommendation.
  10. The detail below: how each phrase was mapped to a technical idea, the extracted fingerprint, the family, the likely root cause (always tagged inferred), predicted category/priority/impact/urgency with their probabilities, and the full evidence chain fold-out.
When the bar is red (novel)The fix area becomes "Route to fresh investigation": no historical fix is recommended, a proposed tier and team are shown, and there are buttons Open a troubleshooting session and How novelty is decided. The nearest analogs are shown for transparency only.

10. Honest limits and FAQ

Limits

  • Most text is synthetic (real tickets had no descriptions). Confidence is capped near 0.8 by design.
  • The exact fix is right on the first try only about 40% of the time.
  • No step-sequence data: "what usually comes next" is not claimed.
  • No assignee or team data: no individual is ever recommended.
  • No environment field: it stays Unknown unless you say it.
  • The novelty test set is small (about 20 per split).
  • The new website has no Live Correlation page; use the API (/incidents/simulate) or the older Streamlit app.
  • Desktop only; no Docker (local processes).
  • Decision support only. It never changes a real system.

Where your work is kept

  • Report text, the last analysis, the session and the evaluated-query list live in your browser tab's session storage: they survive a reload but not a new tab (the list holds up to 50).
  • Incidents, attempts, escalations, feedback, postmortems and knowledge-base changes are saved by the engine in data/processed/incidents.db and the search index.
  • Theme choice is remembered in the browser.
  • Menu status refreshes every 30 s; the Escalations count refreshes every 30 s.
